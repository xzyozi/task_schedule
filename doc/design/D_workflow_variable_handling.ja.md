# 設計提案：ワークフローの変数と状態管理

## 1. 概要

本文書は、ワークフロー内のステップ間で堅牢なデータ共有を可能にする新機能について提案します。目的は、あるステップの出力（例：関数の戻り値やスクリプトの標準出力）をキャプチャし、後続のステップの入力として利用できるようにすることです。これにより、データのチェックを行い、その結果をメールで送信するような、より複雑で動的なワークフローの作成を容易にします。

これは、各ワークフロー実行に永続的な「コンテキスト」と、タスクパラメータのためのシンプルなテンプレート機能を導入することで実現されます。

## 2. コアコンセプト

### 2.1. ワークフロー実行コンテキスト

-   個々のワークフロー実行に関連付けられる、新しいJSONデータストア「**ワークフロー実行コンテキスト**」を導入します。
-   このコンテキストは、ワークフロー実行開始時に初期化され、完了するまで永続化される辞書形式のオブジェクト（キーと値のペア）です。
-   ワークフロー内の各ステップは、このコンテキストへの読み取りおよび書き込みアクセス権を持ち、ステートフルな順次操作を可能にします。

### 2.2. ステップ出力のハンドリング

-   ステップの実行結果をキャプチャするメカニズムを導入します。
-   **Python関数:** `python_job_wrapper.py` を変更し、対象関数の `return` 値をキャプチャします。この値はJSONシリアライズ可能でなければなりません。
-   **シェルスクリプト:** スクリプトの標準出力（`stdout`）をその結果としてキャプチャします。
-   ユーザーは、この出力をワークフロー実行コンテキストに保存するための変数名を指定できます。

### 2.3. パラメータのテンプレート化

-   シンプルなテンプレート構文 `{{ context.variable_name }}` を導入します。
-   ユーザーは、これらのプレースホルダーをワークフローの任意のステップの入力パラメータ（例：Python関数の `kwargs` やシェルスクリプトの `command`）に挿入できます。
-   ステップを実行する前に、ワークフローエンジンはこれらのプレースホルダーを現在のワークフロー実行コンテキストの対応する値に置換します。

## 3. 実装詳細案

### 3.1. データモデルの変更 (`models.py` & `schemas.py`)

1.  **`WorkflowRun` モデル:**
    -   新しいカラムを追加: `context = Column(JSON, nullable=True, default=dict)`.
    -   これはワークフローの変数のライブ状態を保存します。

2.  **`WorkflowStep` モデル:**
    -   新しいカラムを追加: `output_variable_name = Column(String, nullable=True)`.
    -   このフィールドには、ステップの出力を保存するコンテキスト変数の名前を保持します。空欄の場合、出力は破棄されます。

3.  **Pydanticスキーマ:** 対応する `schemas.py` を更新し、これらの新しいフィールドを反映させます。

### 3.2. 実行フロー (`job_executors.py`)

`run_workflow` 関数は、オーケストレーションエンジンとして機能するように大幅にリファクタリングされます。

**ワークフロー開始時:**
1.  空の辞書 `context = {}` を初期化します。
2.  初期の空の `context` を保存して `WorkflowRun` データベースレコードを作成します。

**ワークフローの各ステップにおいて:**
1.  **パラメータ置換:**
    -   実行前に、現在のステップのすべての入力パラメータを検査します。
    -   パラメータ（例：`command`, `args`, `kwargs`）を再帰的にスキャンし、`{{ context.variable_name }}` プレースホルダーを現在のコンテキスト辞書の実際の値に置き換えます。
    -   参照された変数がコンテキストに存在しない場合、ステップはエラーで失敗します。
2.  **ステップ実行:**
    -   置換されたパラメータを使用して、適切なジョブエグゼキュータ（`execute_python_job`, `execute_shell_job`）を呼び出します。
    -   これらのエグゼキュータは、ジョブのキャプチャされた出力を返すように変更されます。
3.  **出力キャプチャとコンテキスト更新:**
    -   ステップ実行後、`step.output_variable_name` が設定されているか確認します。
    -   設定されている場合、返された出力で `context` 辞書を更新します: `context[step.output_variable_name] = captured_output`。
4.  **コンテキストの永続化:**
    -   各ステップの後、データベースの `WorkflowRun` レコードの `context` カラムを更新します。これにより状態が保存され、将来的な「再開」機能の可能性が生まれます。

### 3.3. Pythonジョブラッパー (`python_job_wrapper.py`)

-   ラッパースクリプトは、実行された関数の戻り値を処理するように変更されます。
-   戻り値をJSON文字列にシリアライズし、構造化された形式（例：`{"return_value": ..., "stdout": ...}`）で `stdout` に出力します。
-   `execute_python_job` エグゼキュータは、このJSONをパースして `return_value` を抽出します。
-   戻り値がJSONシリアライズ不可能な場合、ラッパーは例外をキャッチし、ステップの失敗として報告します。

## 4. ワークフロー例

**目的:** データチェックを実行し、結果をメールで送信する。

**ステップ1: データチェック**
- **タイプ:** Python関数
- **関数:** `my_tasks.check_data.validate_records`
- **出力変数名:** `validation_results`

**ステップ2: 通知送信**
- **タイプ:** Eメール
- **件名:** データ検証レポート
- **本文:** `データ検証プロセスが完了しました。結果: {{ context.validation_results }}`

このシナリオでは、`validate_records` によって返された辞書が `validation_results` としてコンテキストに保存されます。その後、メールステップがこの辞書にアクセスし、その文字列表現をメール本文に埋め込みます。

## 5. リスクと考慮事項

-   **セキュリティ:** 提案されている `{{ }}` 置換は単純な文字列置換であり、コードを実行しないため、Jinja2のようなより複雑なテンプレートエンジンで注意深く扱わない場合に生じるリスクを回避します。インジェクション攻撃に対して堅牢な実装を保証する必要があります。
-   **データシリアライズ:** Python関数の戻り値はJSONシリアライズ可能でなければなりません。シリアライズ不可能なオブジェクトが返された場合、システムはステップを失敗させます。この制限は明確に文書化されます。
-   **データサイズ:** 非常に大きな出力（例：ファイル全体の内容）をコンテキストに保存すると、データベースが肥大化し、パフォーマンスに影響を与える可能性があります。ユーザーには、大きなデータはファイルに保存し、ファイルパスをコンテキストで渡すように処理することを推奨します。
-   **エラーハンドリング:** 置換中に変数が見つからない場合や、何らかの理由でステップが失敗した場合、ワークフローはデフォルトで停止し、明確なエラーログを提供します。

## 6. UI/UXの変更

-   Web UIのワークフローステップ定義フォームに、新しいテキスト入力フィールド「出力変数名」が追加されます。
-   メール本文やシェルコマンドなどのパラメータ入力フィールドに、`{{ context.variable_name }}` 構文の使用方法をユーザーに知らせるためのヘルプテキストが追加されます。

# 設計ドキュメント作成・運用ガイドライン

本ガイドラインは、プロジェクトにおける設計仕様書（基本設計、詳細設計、データ構造仕様）の作成、命名、参照、および機械可読運用の標準ルールを定めたものです。
他プロジェクトや別環境への展開・AIエージェント連携・自動化スクリプト連携においても一貫したドキュメント品質と構造化を保持できるよう、以下の規則を順守してください。

---

## 1. ドキュメントの分類とテンプレート選択

作成する設計書の目的に応じて、以下のテンプレートの中から最適なものを選択して作成してください。

| 分類 | テンプレートファイル | 主な記述内容・適用目的 |
| :--- | :--- | :--- |
| **基本設計書** | `TEMPLATE_基本設計書.md` | システム全体の目的、アーキテクチャ方針、コンポーネント分離、システム境界、依存関係の定義 |
| **詳細設計書** | `TEMPLATE_詳細設計書.md` | 特定モジュール・関数の入出力 DTO、状態遷移・シーケンス、エラーハンドリング、単体テスト要件 |
| **データ構造仕様書** | `TEMPLATE_データ構造仕様書.md` | 永続化スキーマ (DAO/State正本)、状態タクソノミー、配置ディレクトリ、原子置換契約、排他制御仕様 |

> **補足:** ※本リポジトリでは設計の骨格となる `BD` (基本設計)、`DD` (詳細設計)、`DS` (データ構造) の 3 種を公式テンプレートとして提供しています。`ENV` (環境構築仕様書) や `OP` (運用詳細設計書)、`PM` (課題一覧) 等は、既存の確定ドキュメントを参考フォーマットとして参照・更新運用してください。

---

## 2. 機械可読メタデータ (YAML Frontmatter) と記法標準

### ① YAML Frontmatter の必須化と正本一元管理
AIアシスタントや自動化スクリプトがドキュメント属性を正確かつ高速に抽出できるよう、全ドキュメントの先頭に **YAML Frontmatter** を配置します。

```yaml
---
title: "基本設計書"
document_type: "basic_design"
version: "1.0"
created_at: "2026-08-11"
updated_at: "2026-08-11"
author: "アーキテクチャチーム"
purpose: "システム全体の目的・コンポーネント分離・責務境界・共通アーキテクチャ方針を明記し、設計のブレを防ぐため"
related_documents:
  - "詳細設計書正本"
  - "データ構造仕様書正本"
---
```

- **二重管理の防止方針**: `purpose`（適用目的）や `related_documents`（関連ドキュメント）などの詳細な属性定義は **YAML Frontmatter を正本 (SSOT)** とします。本文直下の見出しテーブルには視認性確保のための主要メタデータ（文書番号、ドキュメント名、版数、日付、作成者）のみを掲載し、属性の乖離を防ぎます。
- **日付フォーマットの統一**: 機械可読性および表記ゆれ防止のため、YAML 内および本文テーブル内の全日付表記はハイフン区切りの **`YYYY-MM-DD`** 形式に統一します。

### ② 図表・状態遷移表現の標準化 (Mermaid 記法)
マークダウン内でテキスト描画・ネイティブレンダリングを可能にするため、視覚表現には **Mermaid 記法** (`mermaid`) を標準として使用します。

- **全体構造・データフロー**: `flowchart TD` または `graph TD`
- **状態遷移ロジック**: `stateDiagram-v2`
- **モジュール間シーケンス対話**: `sequenceDiagram`
- **データ構造・エンティティ間関係**: `erDiagram` または `classDiagram`

## 3. データ境界ルール (DTO と DAO / 永続化のSSOT分離)

データ管理の混同と関心事の崩壊を防ぐため、データ表現を以下の責務に基づいて明確に分離します。

| データ種別 | 担当レイヤー | 正本ドキュメント | 定義内容 |
| :--- | :--- | :--- | :--- |
| **DTO (Data Transfer Object)** | モジュール間・関数間・ノード間パッシング | **詳細設計書 (DD)** | 関数の引数、戻り値、イベントパケット、ノード間パッシングパラメータの型・バリデーション |
| **DAO / 永続化スキーマ (State正本)** | ストレージ・ファイル保存・永続化 | **データ構造仕様書 (DS)** | ディスクに物理保存されるJSON/DB構造、状態タクソノミー、原子置換・FileLock排他制御 |

---

## 4. 命名ルール方針 (Naming Conventions)

### 標準命名フォーマット
`[PROJECT_PREFIX]-[TYPE_CODE]-[NUMBER]_[DOCUMENT_TITLE].md`

- **`PROJECT_PREFIX`**: 各プロジェクトごとに定義する識別コード（例: `SBOS`, `APP`, `CORE`）
- **`TYPE_CODE`**: `BD` (基本設計), `DD` (詳細設計), `DS` (データ構造), `ENV` (環境), `OP` (運用), `PM` (課題一覧)
- **`NUMBER`**: 3桁連番（例: `001`, `002`）
- **`DOCUMENT_TITLE`**: 日本語タイトル（例: `基本設計書`, `Backend_GPUリース仕様`）

> **文書番号の明記**: テンプレート本文の見出しテーブル内には、本命名フォーマットに対応する **`文書番号`** 欄（例: `SBOS-BD-001`）を必ず設けて相互トレーサビリティを確保してください。

## 5. 参照規約・非コード化・改訂履歴追跡

### ① 特定環境依存ハイパーリンク (`file:///...` 等) の禁止
- 特定マシンのローカル絶対パスの直接埋め込みは禁止。プロジェクトポータビリティを保つため、標準文書名テキストまたは同一リポジトリ内の相対パスリンクを使用すること。

### ② 具象ソースコードの非掲載
- プログラムコードの直接貼付は禁止。パラメータ表、データ型、バリデーション制約、事前・事後条件、失敗契約をテキスト・テーブル・Mermaid図で定義すること。

### ③ 改訂履歴 (チェンジログ) の追跡メカニズム
- 仕様の変遷と「なぜその設計・ルールへ変更されたのか」のコンテキストを維持するため、全ドキュメントの末尾に **改訂履歴テーブル** を設置し、変更理由を明記すること。
